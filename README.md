# Vacation Management

A web application for managing vacation requests.

- **Requesters** submit vacation requests from a booking calendar and follow their status.
- **Validators** (managers) review every request, filter and page through them, then approve or reject (a comment is required when rejecting). Validators can also make their own requests.

**Stack:** Vue 3 + TypeScript + Vue Router + Axios + Tailwind CSS (frontend) · Node.js + [Common Event Framework](https://www.npmjs.com/package/commoneventframework) (backend) · PostgreSQL + TypeORM.

## Project structure

```
backend/
  src/
    root.yaml                 CEF routes: URL + method -> handler
    index.ts                  CEF server entry point
    data-source.ts            TypeORM / PostgreSQL connection
    seed.ts                   Demo users and requests
    auth/                     login, register, logout, me (+ password hashing, input validation)
    users/                    User entity, user handlers
    vacation-requests/
      vacation-request.entity.ts
      commands/               CreateVacationRequest, ApproveVacationRequest, RejectVacationRequest
      events/                 VacationRequestCreated / Approved / Rejected
      handlers/               thin HTTP layer: auth, validate input, call a command
    shared/                   event bus, HTTP error type, auth helpers
    generated/HandlerRegistry.ts   generated by cef-gen-handlers (do not edit)
  scripts/run-local.js        loads .env and starts the built server on PORT
frontend/
  src/
    api/                      Axios instance and API calls
    components/               AppLayout, BookingCalendar, MyRequestsList, PaginationBar, RejectDialog, VacationRequestForm
    composables/              usePaginatedList (shared table loading state)
    stores/auth.ts            logged-in user state
    router/                   routes + role-based guards
    views/                    Login, Register, VacationRequest, Validator, Sorry
```

## Prerequisites

- Node.js 20 or newer
- A PostgreSQL database (local install, Docker, or a hosted one such as Neon)

## Setup

### 1. Database

Create an empty database, for example:

```sql
CREATE DATABASE vacations;
```

You do not need to run any migration: the tables (`users`, `vacation_requests`) and their indexes are created automatically on first start (TypeORM `synchronize: true`, see Known limitations).

### 2. Backend configuration

```powershell
cd backend
copy .env.example .env
```

Edit `backend/.env`:

| Variable | Meaning |
|---|---|
| `PORT` | API port (default `3600`; the frontend dev proxy expects this) |
| `DATABASE_URL` | PostgreSQL connection string. Add `?sslmode=require` for hosted databases |
| `JWT_SECRET_ACCESS` | Secret used to sign JWTs. Use a long random string |
| `ACCESS_TOKEN_NAME` | Name of the HttpOnly cookie that holds the JWT (e.g. `access_token`) |
| `SEED_DEMO_PASSWORD` | Optional. Password for demo users (default `Vacation123!`) |

### 3. Install dependencies

From the project root:

```powershell
npm run install:all
```

(or run `npm install` in the root, `backend/` and `frontend/` separately).

### 4. Seed demo data

```powershell
npm run seed
```

This creates 4 demo users and, for each requester, a Pending, an Approved and a Rejected request. It is safe to run more than once (existing users are skipped).

| Email | Role | Password |
|---|---|---|
| `requester1@example.com` | Requester | `Vacation123!` |
| `requester2@example.com` | Requester | `Vacation123!` |
| `validator1@example.com` | Validator | `Vacation123!` |
| `validator2@example.com` | Validator | `Vacation123!` |

You can also create a Requester account from the **register** link on the login page.

## Run

Start both servers with one command from the project root:

```powershell
npm run dev
```

- Frontend: http://localhost:5173
- Backend: http://localhost:3600 (health check: `GET /health`)

Or run them separately: `npm run dev` inside `backend/` and inside `frontend/`.

The backend has no hot reload. Restart it after backend changes. A Requester is redirected to `/vacation-requests` after login, a Validator to `/validator`.

Other useful commands:

```powershell
cd frontend; npm run build        # type-check + production build
cd frontend; npm run lint
cd backend;  npm run codegen      # regenerate HandlerRegistry.ts after changing root.yaml
```

## API

All routes are served by CEF from `backend/src/root.yaml`. Errors are JSON (`{ "message" }` or `{ "error" }`) with a proper status code: 400 validation, 401 not logged in, 403 wrong role, 404 not found, 409 conflict.

| Method | Route | Who | Description |
|---|---|---|---|
| POST | `/auth/register` | public | Create a Requester account (also logs in) |
| POST | `/auth/login` | public | Log in, sets the JWT cookie |
| POST | `/auth/logout` | any | Clears the cookie |
| GET | `/auth/me` | logged in | Current user (restores the session after a refresh) |
| POST | `/vacation-requests` | Requester, Validator | Submit a request `{ startDate, endDate, reason? }` |
| GET | `/my-vacation-requests?page=&limit=` | Requester, Validator | The caller's own requests, paginated |
| GET | `/my-vacation-requests/booked` | Requester, Validator | The caller's Pending/Approved requests, unpaginated (calendar) |
| GET | `/vacation-requests?page=&limit=&status=&userId=` | Validator | All requests, filtered and paginated |
| GET | `/vacation-requests/:id` | owner or Validator | One request |
| POST | `/vacation-requests/:id/approve` | Validator | Approve a Pending request |
| POST | `/vacation-requests/:id/reject` | Validator | Reject a Pending request `{ comment }` (comment required) |
| GET | `/users` | Validator | All users (id, name), for the user filter |
| GET, PUT | `/users/:id` | self or Validator (GET) · self (PUT) | Read a user, change own name |

Paginated responses look like `{ data: [...], pagination: { page, limit, total, totalPages } }`. `limit` defaults to 10 and is capped at 100.

## Business rules

| Rule | Where it is enforced |
|---|---|
| End date must be after the start date (same day is not allowed) | `CreateVacationRequest` command; the calendar also blocks it |
| A user's requests cannot overlap (Rejected requests don't count) | `CreateVacationRequest` command, inside a SERIALIZABLE transaction |
| Requests in the past are not allowed | `CreateVacationRequest` command; past days are greyed out |
| Only Pending requests can be approved or rejected (approved requests are final) | Approve / Reject commands use a conditional update (`WHERE status = 'Pending'`), returning 409 otherwise |
| Rejecting requires a comment | Reject command (400) and the required field in the reject dialog |
| Only validators can approve or reject | Role check in the handler (403) and route guard in the frontend |

## Technical decisions

- **Commands and events.** Each action is a command function (`commands/`) that validates, writes to the database, then publishes a domain event (`VacationRequestCreated / Approved / Rejected`) on a small in-memory event bus (`shared/event-bus.ts`). Handlers stay thin: authenticate, check role, parse input, call the command.
- **Common Event Framework.** Routes are declared in `root.yaml` with an `x-handler` of the form `<file>#<exportedFunction>`. `cef-gen-handlers` generates `HandlerRegistry.ts` from it. `scripts/run-local.js` loads `.env` and sets the port, because CEF's dev server reads the port from the command line.
- **Authentication.** JWT in an `HttpOnly`, `SameSite=Strict` cookie (not readable from JavaScript, so safer than localStorage), valid for 2 hours. Passwords are hashed with bcrypt and never returned. The role comes from the database for the signed user id, never from the client.
- **Same-origin frontend.** In development Vite proxies `/api` to the backend, so the cookie is first-party and no CORS setup is needed.
- **Concurrency safety.** The overlap check and insert run in one SERIALIZABLE transaction. Approve and reject are single conditional `UPDATE`s, so two validators acting at once cannot both succeed.
- **Pagination.** Offset pagination in the database (`findAndCount` with `skip`/`take`), a stable sort with an `id` tiebreaker, validated `page`/`limit` with a cap, and `total`/`totalPages` in every response.
- **Indexes** on `vacation_requests`: `(user_id, start_date, end_date)` for overlap checks and "my requests", `(status, created_at)` for the status filter, `(created_at)` for the newest-first list, and `(user_id, created_at)` for the validator's user filter.
- **Frontend structure.** Reusable components (`MyRequestsList` is used by both roles, `PaginationBar`, `RejectDialog`), a `usePaginatedList` composable that cancels stale requests so a slow response cannot overwrite newer rows, and a tiny reactive auth store instead of a state library.
- **Frontend behaviour.** Role-based router guards; validator filters and page are kept in the URL (`/validator?status=Pending&page=2`); a 401 on an expired session returns the user to the login page; a server error (5xx) or a submit taking longer than 20 seconds shows a "try again later" page.
- **Team vacation planning.** The booking calendar marks days that are already Pending (amber) or Approved (green) for the logged-in user, greys out the past, and prevents choosing a range that crosses a booked day. Both roles can plan their own vacations.

## Known limitations

- **`synchronize: true`** creates and alters tables automatically. Fine for this assignment, but a real deployment should use TypeORM migrations.
- **In-memory event bus.** Events are published in-process and nothing subscribes to them yet; they are lost on restart. A production version would use a queue/broker (and an outbox) and add subscribers such as email notifications.
- **No automated tests.** Behaviour was verified manually and with API calls.
- **Production serving.** Only the development setup (Vite proxy) is configured. A production deployment would need the frontend built and served behind the same origin as the API (or CORS configured), and `NODE_ENV=production` so the cookie gets the `Secure` flag.
- **Offset pagination** gets slower on very deep pages; keyset (cursor) pagination would scale better.
- **Registration** is open and always creates Requesters. Validators come from the seed (there is no admin screen to promote users).
- **No rate limiting or account lockout** on login.
- **A validator can approve their own request.** There is no separation-of-duties rule.
- **Team planning is per user.** The calendar shows the user's own bookings, not other team members'.
- **Dates are date-only** (no time zones or half days) and weekends/public holidays are not excluded from a request.
